# 开发与发布流程

本文件定义每轮开发、阶段验收和发布的固定闭环。当前进度只看 `PROJECT_STATE.md`，具体架构和契约分别看专项文档。

## 一、阶段门

项目按以下阶段推进，每个阶段结束后必须停下等待用户授权，不能连续跨越：

```text
仓库基建
  -> Provider 探针
  -> 计算约定与 Tool 契约冻结
  -> Provider / Application 实现
  -> DSH Adapter 与真实 Tool Loop
  -> 打包、发布候选与发布
```

阶段计划可以调整，但调整本身需要先记录原因和用户决定。

## 二、活动里程碑

一个可发布版本可以跨越多轮开发，但同一时间只能有一个活动里程碑。

- `PROJECT_STATE.md` 必须链接活动里程碑和当前 iteration。
- 里程碑是用户审核当前版本是否偏离的主要界面，包含范围、目标代码树、TODO、决策门和完成定义。
- 长期架构与 Tool 契约只通过链接引用，里程碑不得复制第二份规则。
- 每轮只更新实际推进的复选项和证据；新增范围或改变完成定义必须先展示 diff 并获得用户确认。
- 里程碑完成后按 `docs/project/milestones/README.md` 冻结、确认并移入 `archive/`。

## 三、每轮开发闭环

### 1. 定位

- 阅读 `AGENTS.md`、`PROJECT_STATE.md` 指向的活动里程碑、相关 ADR 和当前迭代。
- 检查 `git status`、当前分支和用户已有改动。
- 按任务类型读取架构、Tool、Provider、许可证或 DSH 官方真相源。

### 2. 提案与确认

开始实现前说明：目标、非目标、文件范围、依赖/版本、失败行为、验证命令和需用户决定的事项。涉及公共契约、计算默认值、许可证、版本兼容或范围变化时必须先等确认。

### 3. 最小完整实现

- 只完成当前阶段能独立验收的最小职责闭环。
- 不顺手实现下一阶段，不夹带重构，不覆盖用户无关改动。
- 外部依赖、DSH 和 Provider 只通过明确边界接入。

### 4. 分层验证

先跑最小相关测试，再跑当前阶段适用的完整 gate。验证必须覆盖用户最终会经过的组装路径，不能只证明内部函数可调用。

### 5. diff 审核

至少检查：

- 是否越过架构或阶段边界；
- 是否改变 Schema、canonical output、错误或默认值；
- 是否泄漏生日、姓名、地点、私人规划、密钥或第三方原始对象；
- 是否新增共享可变状态、网络、持久化或计划外能力；
- 依赖、lockfile、许可证和打包内容是否一致；
- 文档是否把计划误写成已实现能力。

README 只在用户可见能力、安装方式、用法、版本、限制、隐私或产品定位发生变化时评审。更新前必须对照 README 定位 ADR、最新变更记录和实际版本证据；内部重构、依赖升级、测试结果和阶段进度不得进入 README。

### 6. 持久记录

- `PROJECT_STATE.md`：当前阶段、完成项、阻塞项、验证状态、唯一下一步。
- 活动里程碑：只更新本轮实际推进的 TODO、决策和证据；范围没有变化时不重写计划。
- `decisions/`：只写用户已确认且会长期影响开发的决定。
- `iterations/`：记录本轮目标、实际改动、命令证据、遗留项和建议。
- `CHANGELOG.md`：每轮完成后追加一句开发变更摘要，作为迭代索引；不充当 README 产品版本史。

### 7. 汇报与停点

汇报实际结果、测试证据、跳过项、未决风险和当前 Git 状态，然后等待下一阶段授权。报告“完成”不代表已 commit、push 或发布。

## 四、验证证据矩阵

| 改动                | 最低必要证据                                        |
| ------------------- | --------------------------------------------------- |
| 文档与治理          | 格式检查、链接/私有内容扫描、diff 审核              |
| Domain 规则         | 单测、人工构造边界 golden、穷尽分支                 |
| Provider 映射或升级 | API 探针、contract test、独立差分、版本与许可证审核 |
| Tool 输入/输出      | 输入输出 Schema 测试、每个稳定状态和错误码测试      |
| Observation         | 纯函数测试、snapshot、真实 DSH Tool Loop            |
| 并发或状态          | 重复确定性、A/B 隔离、取消与清理测试                |
| DSH Adapter 或版本  | Cordis 生命周期、Profile 加载、打包产物 DSH smoke   |
| 未来 UI             | Session replay、prepend、live append 最终收敛       |

由被测实现自身生成的 golden 不是独立正确性证据。跳过适用证据必须说明原因并保留为阻塞项。

## 五、日常工程 gate

按当前阶段执行适用项：

```sh
pnpm install --frozen-lockfile
pnpm run format:check
pnpm run lint
pnpm run typecheck
pnpm run test
pnpm run test:offline
pnpm run build
pnpm run pack:smoke
pnpm run dsh:smoke
```

脚本尚未建立时不能伪造同名空脚本；应记录“不适用/未建立”和进入条件。

## 六、GitHub PR 与合并门禁

- `main` 不直接提交，所有变更先进入符合仓库命名规则的短期分支，再通过 PR 合并。
- PR 采用 squash merge，合并后删除远端分支；提交与 PR 标题使用 Conventional Commits。
- 所有者发起且已获得本轮授权的 PR，可以在必需检查全部通过后启用 auto-merge。
- 外部作者的 PR 即使工程 CI 全绿，也必须先由仓库所有者完成业务审查并添加 `owner-approved` 标签。
- CI 负责格式、静态检查、类型、测试、构建、打包和最低 Node.js 兼容证据；它不代替 Tool 契约、计算默认值、许可证或发布决策门。
- 需要改 CI、分支规则、合并方法或协作权限时，先更新对应 ADR；不得在功能 PR 中静默放宽门禁。

## 七、发布闭环

发布不是普通开发动作。准备发布时单独执行：

1. 提交发布提案：版本号、精确 DSH 兼容版本、变更范围、风险和回滚方式。
2. 获得用户对发布候选的确认。
3. 从 frozen lockfile 完成干净安装，运行全部适用 gate。
4. 安装实际 tarball，验证导出、Profile/Bundle 加载和真实 Tool Loop。
5. 审核版本、exports、打包文件、许可证、隐私、README、Changelog 和兼容声明。
6. 展示最终 diff、测试日志摘要和发布候选 tarball 信息。
7. **再次获得明确授权后**，才允许创建/推送 Tag、创建 Release 或发布 npm。
8. 发布后从公共源重新安装，执行最小 smoke，记录发布证据和已知限制。

Tag、Release、npm 发布和 push 的授权不能从“继续开发”推断，也不能跨轮沿用。
